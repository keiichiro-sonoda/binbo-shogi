**2. 単位・損失・clamp・詰み: 実装は整合、教師間の較正は同一とは限らない**

ローカルのやねうら王では `source/evaluate.h:124` の `PawnValue=90`、`source/usi.cpp:1106` の表示変換が `100*v/90`。T146 の `internal_score()` はその整数変換を正しく戻す。通常値について、全 part の `raw_scores` から逆変換した値と `scores` を照合し、**不一致 0**。USI 表示 cp をそのまま保存した、後手だけ符号を反転した、といった不具合は見つからない。

区別すべき数字は次の三つ。

| 数字 | 今回の扱い |
|---|---|
| やねうら王の内部 Value | T146 の保存値。NNUE の出力整数を `FV_SCALE=16` で割った評価値と同じ側の単位 |
| USI 表示 cp | 内部値の約 `100/90` 倍。表示値との比較ではこちらへ変換する |
| WS-T の `1200*atanh(v)` | 旧ラベルの尺度。`sigmoid(x/600)=(1+v)/2` は代数的な関係であり、内部 Value と同じ較正の証明ではない |

`trainer/train_nnue.py:539` は float の目標を ±2000 に制限し、予測 `forward*600` と Huber δ=600 で直接回帰する。**cp objective の 600 は、ラベルを勝率へ変換する温度ではない。** `trainer/nnue.py:39` と export は出力層に `FV_SCALE*600` を織り込むので、配備後の内部評価値も学習時の `forward*600` に対応する。新ラベルをさらに `100/90` 倍しなかったことは、この接続では正しい。

したがって、旧 WS-T と同じ数値分布でないこと自体を「単位バグ」とは呼べない。ただし固定された δ と clamp が教師ごとに同じ割合の情報を残す保証もない。まず warm-start の対照では尺度・δ・clamp を据え置き、初期値と学習量の変更を評価するのがよい。旧平均へ合わせる補正や一律 0.9 倍を先に足す根拠はない。

全ラベルを走査した分布は以下。特記なき値は内部値または旧ラベルの保存尺度。**提示された +45 / −187 は生平均でなく、±2000 制限後の平均である。**

| split / ラベル | 生平均 | 制限後平均 | 制限後標準偏差 | \|保存値\|≥2000 |
|---|---:|---:|---:|---:|
| train 新 | +1014.8 | +45.78 | 1178.73 | 14.2602% |
| train 旧 | −284.2 | −186.36 | 951.45 | 14.2482% |
| val 新 | +100.3 | +38.65 | 1149.08 | 12.1600% |
| val 旧 | −198.9 | −161.28 | 943.73 | 13.5380% |

新旧 train の clamp 率はほぼ同じで、**「新教師は大量に clamp されるから失敗した」は支持されない**。ただし制限後標準偏差は約 24% 大きく、同じ率だから同じ目標分布というわけでもない。4M 行ずつの 16 ブロックで制限後相関は **0.8883〜0.8903**。一部だけ違う順序で結合された兆候はない。

詰みは `mates` フラグで train **2,542,775 行 (約 3.98%)**、val **186 行 (0.372%)**。train の正の詰みは 2,367,798 行で、強い正負の非対称が生平均を大きくする。全件でフラグ付きラベルは正負とも ±32000 になり、学習では ±2000 へ落ちる。なお、`|score|>=30000` の率は train 4.202%、val 0.590% であり、**詰みフラグの率と同一ではない**。これらを混同してはいけない。距離情報を捨てる設計は確認できたが、オーバーフローや片符号だけの未制限はなかった。

**3. 局面・手番・データ接続: 標本と全 part で整合を確認**

`kp.canonical_shared_row_to_sfen()` は own 39 列から手番・盤駒・持駒、自玉を復元し、opp 側の anchor から相手玉を戻す。own だけの復元成功で安心せず、独立の cshogi Board から **77 列全部を再計算**した。

| 検査 | train | val |
|---|---:|---:|
| decode → cshogi → re-encode 全列一致 | 2048 / 2048 | 1024 / 1024 |
| 復元した先手番 / 後手番 | 981 / 1067 | 519 / 505 |
| 持駒あり / 成駒あり | 1814 / 1168 | 908 / 590 |
| part の行番号・手番・assembled ラベルと一致 | 2048 / 2048 | 1024 / 1024 |
| compact 復号が元 77 列と一致 | 全標本一致 | 全標本一致 |

compact の source stamp (実体パス・サイズ・mtime・先頭末尾 hash) も両 split とも現在の入力に一致。古い局面キャッシュへ新しいラベルだけを誤接続した兆候はない。

さらに元 HCPE を使い、val は 5 シャードから各 200 行の **1000 / 1000**、train は run32m_g の「置換されていない」512 行で **512 / 512**、元の盤面・手番・持駒と復元 SFEN、77 列が一致した。置換された train の元 PSV は生成後に削除されており、その全行を元ファイルから独立復元したとは主張しない。今回の全列往復は、成駒・持駒・両手番を含む復元器の検証になる。

T146 はこの SFEN をそのまま `position sfen` に送り、追加の色反転なしで探索する。加えて train の区切り **[1,234,000, 1,235,000)** と **[45,000,000, 45,001,000)** を同じ条件・順序で実際に再探索した。**2000 / 2000 行で内部値、表示値、深さ、nodes、詰みフラグが保存 part と完全一致**した。少なくとも標本では、ログだけの手番が正しく、別の手番を探索していたという問題もない。

SFEN の手数を 1 に戻すため対局履歴・千日手履歴までは復元しない。今回確認した「同じ局面」は盤面・手番・持駒の同一性であり、過去の手順を含むゲーム状態の同一性ではない。これは今回だけの新しい符号バグとは区別する。

全 **64,000 part / 64,000,000 行**では、各ファイル名の行範囲、連続した `rows`、recipe ID、assembled 配列との値一致、通常値の逆変換、詰みの絶対値を確認し、すべて不一致 0。assembled train / val の SHA256 も `labels/meta.json` と一致した。

**4. TT と node cap: 主因となる破損はないが、探索値は局面だけの関数ではない**

Claude 追記どおり、初期化は 1000 行の part の先頭だけ。TT **と探索履歴**を内部で引き継ぐ。したがって、教師値は「局面 + それ以前の同 part の局面列」の関数であり、各局面を単独・空の探索状態で読んだ値ではない。固定 part と固定順序が必要で、プロセスの割り当てだけなら再現できることは上の再探索とも整合する。

無作為 96 train 行を、各行で初期化して depth 9 で読み直した。保存ラベルとの ±2000 制限後の差は **MAE 56.2、中央値 23.5、95 percentile 217.0、相関 0.9974**。正負が変わるのは 7 / 96 行。双方が ±500 内の 46 行でも MAE 51.7 だった。極端値込みの相関だけで「影響ゼロ」とは言えず、接戦では数十〜数百の揺れがある。ただし、行ずれや全体反転のような破壊的な不整合ではない。

全 part の深さ・nodes の検査結果:

| 指標 | train | val |
|---|---:|---:|
| 非詰みで depth < 9 | **15 / 63,950,000** | 0 / 50,000 |
| 詰みで depth < 9 | 1314 | 0 |
| 保存された nodes ≥ 10M | 11 | 0 |
| 保存された最大 nodes | 14,352,507 | 821,497 |

詰みの早期終了と cap による未完了反復は分ける必要がある。少なくとも depth 不足の非詰みラベルは約 **0.0000235%** で、全体の −100 Elo の主因とする規模ではない。最後の bound なし PV を保存する実装も妥当。nodes はその PV 出力の値であり、上限停止時の全消費量や厳密な cap 到達フラグではない。上限を超える行があることだけで cap 無効とは判定しない。

再開の監査性には改善余地がある。`t146_self_relabel.py:407` は `node_cap` を recipe の固定条件から外し、既存 part の **最後の exact 出力の nodes** より cap が大きいことだけを検査する。この条件だけでは、その後の未完了反復で cap を超えていなかったことを証明できない。また、script hash を無視する再開は任意のコード変更に安全な仕組みではない。次回は cap・完了深さ・最終消費 nodes を明示して provenance に固定するのがよい。今回の全件検査と再探索からは、全量をやり直す根拠は得られなかった。

**8. Claude の診断への回答**

**支持する部分:** 有限の局面集合で自分の探索値を静的ネットへ圧縮し直す際に、改善信号より近似・汎化の損失が勝つ、という説明は十分ありうる。実際に W は教師である task142 より約 100 Elo 弱く、教師の静的ネットよりも検証で新ラベルへの誤差が大きい。warm-start は既存の表現・広い局面での知識を残せるため、合理的な次の一手である。

**断定できない部分:** 今回から「64M の自己 depth-9 ラベルでは原理的に教師を再現できない」「水匠が成功した理由は教師の強さだけ」とは言えない。

- W は新ラベルへかなり適合している。問題は未学習行への移り方と探索での有用性であり、単なる最適化未完了とは異なる。初期値・lr・周数を切り分けた比較はまだない。
- **Task 145 は教師だけでなく、局面集合も丸ごと水匠の集合へ変更している。** +102.5 は「同じ形・同じ行数・ほぼ同じレシピのデータセット比較」で、同じ局面のラベルだけを替えた因果効果ではない。局面の広さ・質、ラベル雑音、両者の組み合わせが交絡する。元報告の「ラベルを水匠にするだけ」という表現は狭めるべき。
- こちらの局面は Gikou 自己対局を task109 で静止化したもの。task142 自身が選ぶ手・探索中に訪れる局面・現 eval で止まる qsearch leaf と同じ分布ではない。現在の強い eval の知識を、その限られた集合から再構築するのは難しい可能性がある。今回直接測ったのは train/val の分布差と実戦への移り方で、探索中全 leaf の分布比較ではない。
- TT/履歴と深さによる揺れは実在する。決定的に再現できる探索値でも、同じ盤面を安定した教師値へ写すという意味での雑音はある。探索自身の誤り・枝刈り・bootstrap の偏りも自己ラベルでは消えない。
- 新ラベルは旧ラベルより平均も分散も違うが、平均の修正だけでは改善も劣化も説明できない。task142 が水匠の仕上げで得た知識を W が十分回収できなかった、という仮説にも合う。

参考に、[やねうら王の公式学習 Wiki](https://github.com/yaneurao/YaneuraOu/wiki/評価関数の学習) は、自分で生成・学習を繰り返す経路と qsearch leaf の重要性を説明し、通常探索の数値には雑音が多いとの見方も示す。[開発者による depth の考察](https://yaneuraou.yaneu.com/2020/02/06/教師生成時のdepth問題に関する考察wcsc29優勝記より/) は追加学習・浅い教師からの段階的な学習にも触れるが、比較不足という留保付きである。これらは warm-start の動機にはなるが、**「通常は継続学習だから今回の原因は初期化」と証明する資料ではない**。また、ここで挙がる lambda や eta を、この trainer の cp Huber・Adam の値へそのまま移してはいけない。

自分の深い探索を学ぶ方法にも、そのたびに強くなる保証はない。現在の eval を f、探索値を T(f)、静的ネットへの当てはめを P とすると、今回の処理は概念的に `P(T(f))`。`T(f)` の質が改善していても、制約された局面集合上の P と、再びそのネットで行う探索の組み合わせが強くなるとは限らない。この観点は、作者の「自分で強くする」方針と両立する。

**9. Task 150 を具体化するなら**

最初は提案の 2 本でよい。既存 64M とラベルを再利用でき、これ以上の教師生成を待たない利点が大きい。優先して lr `5e-6`、次に `1e-5`、各 **1 周固定の final**。この lr 順の優劣は未検証で、安全側から試す実務上の推奨である。

| 条件 | 推奨する固定内容 |
|---|---|
| 初期値 | **task142_finetune / nnue_final.pt**。採用 nn.bin は `651ff927…` |
| データ | shared_64m_qs129 全 63,950,000 行、T146 新ラベル。val も同じ新ラベル |
| 学習 | QAT / tie / Factorizer / mirror / fast、batch 1024、fresh Adam。scale 600、δ600、clamp 2000 は維持 |
| アーム | lr 5e-6 と 1e-5、別の新規 out、各 1 周。前のアームから継がない |
| 書き出し | 各アームの final。0cp gate と、開始重み・export 元の対応を記録 |
| 主判定 | 公開データで再仕上げする前の候補 − task142。指定 3 組、対応を保った差、両物差し別も表示 |
| 採用確認 | 2 本から選んだ後、未使用の間隔を空けた seed 組で確認。探索用 3 組の勝者だけで採用しない |

`--resume` が既存 state を読むと `--init-weights` 後のモデルと optimizer を上書きする。新しい out を必須とし、学習率を変えるために前の out を再使用しない。task142 の `nnue_best.pt` は旧 WS-T val が良かった ep1 で、採用したのは ep2 の final。**warm-start のファイル名の取り違えは、今回発見した現在の不具合ではなく、次回避けるべき具体的な落とし穴である。**

同様に trainer は epoch 0 を `best` 候補に含めず、`best_val=inf` から始める。warm-start が初期値より悪化しても、何かの学習後の重みが best として保存される。epoch 0 の診断値と採用 eval 自体を必ず残す。新教師 val の改善だけを成功条件にしない。

更新は `ceil(63,950,000/1024)=62,452` step。Task 142 は `2*ceil(7,240,673/1024)=14,142` step。従って同じ lr 1e-5 なら更新回数は **4.42 倍**。lr 5e-6 でも更新回数を半分にしたわけではない。Adam・QAT なので `lr*step` だけで重み変化が決まるわけではないが、少なくとも「水匠の仕上げと同程度に軽い」という説明は避けたい。

**10. 機械時間当たりの優先順位と分岐**

時間は過去の fast 学習 1 周約 519〜563 秒、従来の判定約 40〜45 分を目安にした将来の概算。実測していないジョブの所要時間を保証するものではない。2 本を精密に測る費用は学習より対局が支配する。

| 順位 | 次の実験 | 価値と費用の目安 |
|---|---|---|
| **1** | **上記 warm-start 2 本** | 新規生成なし。学習合計約 18 分 + 判定 2 回。現在の知識を維持しながら新ラベルを使う直接の試験で、作者の本線に最も合う |
| **2** | 学習量を減らす試験: 全域から一様な 8M 行、warm-start 1 周 | 両方悪化、または変化が大きすぎる場合。学習は約 1 分 + 判定。全 64M の 1 周より小さい介入を試せる。**先頭 8M の prefix ではなく全 run から同じ固定標本を取る** |
| **3** | 新探索値と現 task142 の静的値をブレンド | 同じ局面で `y=(1−λ)*clip(f142_static)+λ*clip(new_d9)`、まず λ=0.5 を 1 点。再探索不要、追加の静的 forward が必要。既存の知識を目標にも残す。まず小標本で十分 |
| **4** | W の ep12 を既存重みから対局評価 | 学習不要、判定 1 回。周選択と Elo のずれを確かめる診断。ただし ep12 は新 val と実戦静的診断とも改善せず、100 Elo を取り返す本命にはしない |
| **5** | 現 binbo が作った新しい局面の小集合 + d9 / d12 | warm-start でも伸びない場合の本線。現 eval で静止化し、同一局面の教師深さを比較する。今回の 512 行では d12 の教師品質がよかったが、全量 d12 に進む前に 1〜数M 行で棋力まで確認 |
| **6** | 全 64M の d12 再ラベル、ゼロからの再学習の反復 | 生成・学習コストが大きく、今は初期値・学習量・分布を切り分けられていない。先に行う理由が弱い |

lambda は **新探索ラベルの重み**という定義に固定する。これは trainer の `--cp-result-lambda` (実戦結果との混合) でも `--wdl-lambda` でもない。既存 CLI に同じ意味の機能があると誤解して渡してはいけない。静的値と新ラベルをそれぞれ制限してから混ぜれば、詰みの ±32000 が混合を支配しない。

旧 WS-T との混合も安く作れるが、現採用 eval ではなく弱い旧教師の悲観的な尺度へ戻す拘束となるため、**現 task142 の静的値を錨にする方を優先**する。単に 0.5 を混ぜれば最適、という根拠はなく、最初から多数の λ を走らせる必要もない。

既存の水匠 7.24M を 5〜10% replay する案は、pure warm-start が水匠で得た知識を忘れる場合の次候補にはなる。ただし入力分布・教師も変えるため、最初から混ぜると自己ラベルの効果を測りにくい。作者の方針に従い、**追加の公開データ取得は勧めない**。水匠仕上げを再び行うなら、まず自己ラベルだけの前後を測り、仕上げの量を基準と揃えた別の結果として示す。Hao / tanuki- の学習利用も勧めない。

判定の読み方も先に決める。warm-start が強くなれば次の反復の資格になるが、今回の scratch との差には lr・周数の差もあり、「初期化だけが原因」とまでは言わない。新 val は下がるのに対局が弱くなるなら、epoch を増やす前にブレンドや局面分布を見直す。2 本とも差なしなら、小さな改善を検出できていない可能性を残し、直ちに雑巾絞り全般の否定へ広げない。

**11. 再現条件と検証の限界**

パスはすべて `source scripts/env.sh` の `$DATA_ROOT` / `$VENV_PY` を使用した。Python は bytecode 書き込みを止め、CPU forward では CUDA を非表示にし、torch intra-op=8 / inter-op=1。探索プローブのコードは既存 `t146_self_relabel.Engine` を利用し、manifest の options、depth、cap 10M を渡した。前述の実験以外のエンジン実行は行っていない。

- forward の seed は `default_rng(20271470)`。train 63,950,000 行から `choice(8192, replace=False)` を昇順にして評価。val decode は続く RNG から `choice(50000,1024,replace=False)`。上表の train decode は、別 seed `20271473` で全 63,950,000 行から `choice(2048,replace=False)` した標本 (最小行 8493、最大行 63,906,290)。forward の val は全行。
- 原 HCPE 照合の seed は `20271472`。val シャード 95〜99 の順に各 200 行を choice。続いて train 後半の行を `integers(31950000,63950000,2048)` で選び、`work/task129/changed.npy` が false の先頭 512 行を原 HCPE と比較。
- 探索プローブの seed は `20271471`。train から `choice(63950000,96,replace=False)` を昇順にする。次に Task139 の TSV 順の有効行から 512 行を choice して昇順にする。有効条件は binbo/tanuki/aoba/wst_s8 が全て cp、`|tanuki_v|<=1500`。各深さで同じ 512 行を固定 128 行ずつに区切り、各区切り先頭で reset。96 train 行は行ごと reset。
- QAT forward は各モデルの `collapse_map` と Factorizer を読み、`fake_quant=True, sparse_ft=True`、512 行ずつ own39 / opp38 を `QATSharedNNUE` へ渡し、出力に 600 を掛けた。task129 は best、task142 は final、W は best と final、WF と水匠生徒は final。各モデルは eval mode、勾配計算なし。
- 全件 part 検査は `parts/*.npz` を train/val のファイル名範囲へ対応させ、`rows == arange(lo,hi)`、recipe ID、`scores == assembled[rows]`、通常値 `sign(raw)*ceil(abs(raw)*90/100)`、詰み `abs(scores)==32000` を照合。深さ・nodes・詰み率もここから集計した。

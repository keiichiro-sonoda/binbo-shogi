# Task 078 — M3: MCTS 自己対局ループを M2 ckpt から回し「出発点を超える」を検証((c) 本丸)

**目的**: M2 の warm-start ckpt(value corr 0.90 / 方策乱数、champion 比 ≤−730)から **Gumbel AZ 自己対局ループ**をフル将棋で回し(学習信号= MCTS 訪問分布+自己対局勝敗のみ、技巧2系ラベル不使用)、**出発点を有意に超えるか**を USI 対局で判定。066-072「αβ蒸留では初期化点を自己対局で超えられない」への直接の答え合わせ。実測 2026-07-02〜03、RTX 4060 Ti 16GB、隔離 `~/task074_frameworks/pgx/examples/alphazero/`(m3_*.py、非コミット)、**リポジトリは文書のみ・Rust 無改変**。

## ループ設定と lr の実測選定(想定外だが計器が機能した点)
- 構成= M1 動作点そのまま: sims32 / 64ch×5L / batch256 / steps512 / minibatch1024(=128 updates/iter)。初期値= M2 `value_distill_best.ckpt`、adam は fresh。
- **plan 既定の lr=1e-3 は 1 iter で蒸留 value を全壊**: 新設の **val_corr_m2 監視**(ckpt ごとに M2 val 50k で教師一致度を測る)が初回 ckpt で **0.90→0.0075** を検出(独立再評価で確認=監視自体は正)。fresh adam × 1e-3 × 128 updates が原因。
- **lr ladder を 2-3 iter で実測**: 1e-3 → 0.0075@iter1 ‖ **1e-4 → 0.57@1 / 0.50@2 / 0.53@3**(policy_loss は 6.94→5.34 と学習進行)→ **本走は lr=1e-4**(「必要なら微調整を明記」条項の適用)。監視が一晩を無駄にする前に 4 分で検出=計器の設計意図どおり。

## M3 判定 = **FAIL(主判定 accept_h0 — 本予算では出発点を超えられず)**
事前固定の合格条件(SPRT accept_h1)不成立。延長基準(終端 2 点上昇 > +5% は満たすが**最終点 score 0.346 < 0.55 で不成立**)も文言どおり適用し、1 晩で打ち切り測定(基準の事前固定は動機づけられた延長を防ぐためのもの)。

**切り分け(事前に決めた順序で)**:
- **(a) 損失は動いたか → YES**: policy_loss 6.94→~1.0、対局は決着型に回帰、カーブは V 字=**ループは学習している**(死んだループではない)。066-072 の「何をしても不動」とは様相が違う。
- **(b) value は壊れたか → 部分的に YES(主因)**: lr=1e-3 は 1 iter で全壊(監視が検出)。採用した 1e-4 でも教師一致 0.90→0.2-0.4 帯=**蒸留 value の質を大きく手放した**。主判定の相手(warm-start)は 0.90 の value を保持したまま=ハンデ戦の構図。
- **(c) 方策は育ったか → YES(直接対局で確定)**: **iter150 vs iter10 の直接対局 = 25-25-10/60, score 0.625, elo +89(CI +23..+161)**=世代間では有意に強くなっている。一方どちらも warm-start へは ≈−110 で同水準=**強さの非推移性**: ループ内(自己対局で形成された similar な棋風同士)の改善が、異質な相手(intact value 0.90+乱数方策)への成績に転写されていない。value の失分を方策の成長が(この相手に対しては)取り返せず終端 −110。
- **結論**: 本 FAIL は「自己対局が新知識を生めない」(066-072 型)ではなく、**「warm-start の保持と方策の成長の両立」が本設定(fresh adam・全パラメータ共通 lr・150 iter)でできなかった**という設定問題+予算問題。ループ自体の学習力は **世代間の直接対局(+89 elo)** と決着型回帰で確認できた=自己対局 RL が「正の強さ差」を生むこと自体は世代間では観測されている(出発点比ではまだ)。

## 詰まりどころと学び(実測)
- **fresh adam × lr1e-3 は warm-start を 1 iter で消す**(蒸留初期化を使う場合の必須注意)。監視(val_corr_m2)を最初から入れたことで 4 分で検出、lr ladder 15 分で本走 lr を決定。
- 監視指標の解釈: val_corr_m2 は「教師一致」であり強さではない。RL 中の低下は仕様(自分の分布への特化)、**初回の急落だけが破壊のシグナル**という使い分け。
- AZ-vs-AZ 対局は gumbel_scale=0 で決定的 → 分散は「ランダム開幕 6 plies × 先後入替ペア」で確保(固定開幕ブック×決定的エンジンの標準形)。sims 固定なので GPU 並走でも強さは不変(時間のみ変化)=カーブ測定は並列可。

## M4 への申し送り(一変数の候補、推奨順)
1. **方策 warm-start(案2、推奨)**: hcpe の bestmove(one-hot)で policy head も事前学習してからループ。序盤から対局が意味を持つ=「無目的対局の谷」を丸ごと回避し、value 教師(勝敗)の質も上がる=今回の両失敗因を同時に叩く。M2 で温存した切り分けの出番。
2. **value 保全**: fresh adam × 共通 lr が warm-start を壊すのが実測主因。対策候補= M2 蒸留データの value replay を初期に混ぜ徐々に減らす(067 の轍に注意しつつ初期化保護としてのみ)/ adam warmup / lr さらに減。
3. **iter 延長(ckpt150 から resume)**: V 字終端の勾配は正(100→150 で +160 elo)。もう 1-2 晩で出発点を越えるかは未検証=安価に足せる確認(延長基準は今回の文言を「反発局面」に合わせて再設計)。
4. `max_num_considered_actions`(既定 16)↑: 方策が弱い間の探索幅を広げる。
- 判定系はそのまま流用可(m2_match+m3_sprt、非合法手 0 の実績 895 局)。ループも m3_loop の resume/監視/watchdog がそのまま次の実験基盤。

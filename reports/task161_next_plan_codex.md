# Task 161: 次に何をするか — Codex の提案

2026-10-22。Task 160 の結果は未取得として書く。指定資料、設計、関連スクリプトを読んだ。エンジン、学習、GPU、全量データ走査は実行していない。変更は本報告だけ。commit / push はしない。

## 私の判断

**自己対局の本線を続ける。ただし「次の世代へ進めばまた +30」を期待する運用はやめる。** 当面は、過去の局面を残すこと、捨てていた局面を正しく戻すこと、新しい局数を増やすことを比較する。容量の拡大より先である。本番設定での確認には、研究と別に時間を確保する。

Task 154 は成功した。Task 159 は小さな改善を否定できない。これだけでループの天井とは言えない。一方、同じ形の公開 eval が強いことは、512 幅が必要だという証拠にもならない。256 幅のままで改善できる余地がある。

「自分の局面と勝敗が要点」という説明は、現状では少し強い。Task 154 の評価値だけの E も +17.0 だった。R は E より点推定で約 +11.5 だが、勝敗だけで全改善を説明できない。Task 150 との違いには、局面、初期値からの学習量、教師の探索状態もある。アピールでは「この組み合わせで改善を確認した」と言うのが正確である。対照を増やす価値はあるが、説明を完成するためだけに多数の棋力判定を買う必要はない。

## 1. 2 周目が小さかった理由

私の第一候補は、**初回に取れた分を取ったことと、狭い新規データへの再適合**の組み合わせである。浅い自己教師の共通の見落としが、その先の伸びを制限している可能性もある。ただし、まず「本当に伸びが減ったのか」を留保する。

- 初回 +28.6 [+14.3, +42.9] に対し、2 回目は +12.0 [−3.3, +27.2]。初回の採用前確認は +19.5 だった。選ばれた初回の点推定だけを基準にすると、減速を大きく見やすい。
- 2 回目は 3 組とも +9〜+16。対 tanuki- は −2.9、対 AobaNNUE は +25.5。全般的な劣化より、改善の小ささや相性を疑う。
- 2 周と 4 周の点推定差だけで過学習を確定しない。候補間の対応を保った直接の差が必要である。
- 2 回目の学習行は 10.28M → 9.83M。約 4.4% 減であり、半減ではない。局数は同じ 15 万局。「データが少なくなったから」で約 17 Elo の差を説明し切るのは無理がある。

| 原因候補 | 今の重み付け | 安い識別方法と読み方 |
|---|---|---|
| 判定ノイズ、初回の選択による上振れ | 最初に留保する | 保存 TSV の同じ開局・先後をそろえ、`(159e2−154)−(154−142)` を再標本化する。同じ開局の両アンカーもまとめて抽出する。追加対局なし。差を確定できなければ「減速」は仮説のまま |
| 初期値の違い、改善の逓減 | 有力 | 同じ round 2 データを task142 から学習する。後述の順位 2。出発点が強いほど伸びしろが減ることと、データが悪いことを分ける |
| 新規データだけへの適合、過去の知識の喪失 | 有力だが未証明 | 局単位 holdout の誤差と、水匠の既存固定標本への誤差を初期・1・2 周で比較する。前者が改善し後者が悪化するなら replay の動機になる。棋力の代用にはしない |
| QS drop の終盤偏り | 実在。ただし減速の直接原因は未証明 | round 2 でも ply・終局までの距離・評価帯別の保持率を取る。round 1 にも同じ偏りがある。round 2 の層構成・保持率がさらに変わったかが重要 |
| depth 9 の雑音、共通の誤評価 | 有力な上限候補 | 同じ葉の小標本を d9 / d10 / d11 / d12 で読む。到達深さ、差、符号変化、時間を記録する。後述の順位 6 で棋力まで対照化する |
| 強い側の対局が単調になる | 現状は証拠不足 | 各回から同じ数の局を取り、16/32/60 ply の局面重複、飛車分類、玉配置、長さ、評価帯の分布を比較する。round 1 の序盤重複は少なかった。盤面が違うだけでは戦型の多様性は保証しない |
| 更新量が大きい、Adam の初動 | 可能性あり | 同じ標本・同じ目標で lr だけ半分にする。途中重みを残す。Task 150 C の失敗があるので「小さく動かせば安全」とは言わない |
| 符号・eval 指定などの実装事故 | 第一候補にはしない | Task 156 は round 1 の配線を支持。Task 159 のコードは gen / QS とも task154 を明示している。ただし round 2 全件を監査済みとは言わない。manifest と少数棋譜で再確認する |

追加の読み取り診断は、まず 1 スレッド、各回 1,000 局程度、数分で切る。全量監査を毎回繰り返さない。重みの forward や探索が必要な診断は、現在の時間つき対局が終わってからにする。本相談では実施していない。

## 2. 費用と判定の共通条件

以下は将来の実行案である。今は起動しない。

- 生成は 26 プロセス、Threads 1、depth 9、Hash 16MiB、node cap 10M。15 万局 2.5h、QS 17 分を基準とする。詰み読み切りで終局し、通常評価の閾値では終わらせない。最大 320 ply はまず維持する。
- 学習は 10M 行 × 1 周で約 3 分を予算にする。QAT / tie / Factorizer / mirror / fast、FV16、batch 1024、lr 1e-5、勝敗 30%、final を基本とする。初期重み、生成 eval、QS eval、seed、総提示行数を別々に記録する。
- **J = 3 組 × 2 アンカー × 800 局、約 45 分/候補**。予定枠は負荷や入出力も含め最大 90 分/候補を見ておく。学習が 3 分でも候補を増やし放題にはしない。
- 主判定は既存の spaced seed 3 組の pooled 差。CI 下限 > 0 の候補だけ、新しい確認組と micro へ進む。確認は約 40 分を別枠に置く。確認の合算と micro の点推定が両方 > 0 なら採用候補。採用は作者の判断である。
- 新採用版の主判定 frame がなければ、基準側にも J が要る。新しい対照を作る実験では、その J も数える。候補を見てから組を足し、既知の結果と合算して救済しない。
- ゲーム単位の独立 holdout を診断用に確保する。既存 154 / 159 の学習集合から後で抜いた標本は holdout ではない。別の未学習局か、次の生成で先に分けた局を使う。初期重みが学習済みの局も、未学習とは扱わない。旧 WS-T val の最良周で選ばない。対局による採用規則は変えない。
- 表の期待利得は**私の主観的な狙い幅**である。統計的予測区間ではない。悪化もありうる。各改善を足し算して大会までの Elo を予報しない。

## 3. 次の 8 件 — 優先順

### 1. 本番条件の確認を先に予約する

**仮説:** ノード固定で得た改善が、長い時間、28 スレッド、ponder、通信を含む実戦でも損にならない。

レシピ: 現採用版でローカルの本番ブイ対局を先後 2 局ずつ。Xubuntu、Threads 28、Hash 8192MiB、ponder あり、定跡なし、FV16、CSARule27、512 手、NetworkDelay 120 / 1120 を runbook とそろえる。秒読み際の `ponderhit / stop`、再ログイン、宣言、512 手境界の既存 fixture を通す。全 30 局の初期検証を最初から反復する必要はない。

外部への試験は別途作者の指示がある枠で行う。floodgate は新候補で 4〜8 局を目安にする。10/22 朝の task154 の 4 戦 4 勝は既に記録にある。ただし相手は 2 者で、これだけでは強豪相手や長い接戦を確認できない。全力の 28 スレッド同士を同じ PC に 2 本置かない。ローカル試験で相手と資源を分けた条件と、floodgate で単独稼働した条件を区別する。

費用: ローカル約 2h、floodgate 2〜4h、境界・復帰確認約 30 分。合計 4.5〜6.5h の専用枠。J は不要。最終候補に替えた後もローカル 4 局、約 2h を確保する。

期待: Elo の加点は見込まない。時間切れや誤配備による敗戦を防ぐ。少数局の勝率は採用根拠にしない。時間切れ、誤宣言、プロトコル異常が 1 件でもあれば、その原因を解消するまで研究より優先する。時間制だけで弱く見える場合は、局数不足と速度低下を分け、直ちに eval を戻したり時間設定を細かく振ったりしない。

### 2. 必要なら 1 本だけ、出発点をそろえる

**仮説:** round 2 のデータにも価値はあるが、既に round 1 を学んだ初期値からの連続学習では利益が小さい。

レシピ: **task142 final → round 2 の既存 9.83M → 2 周、lr 1e-5、勝敗 30%**。Task 159 e2 とデータ、行順の seed、学習設定をそろえる。Task 154 R とも同じ 3 組で比べる。データ生成はしない。

費用: 学習約 6 分 + J = 約 51 分。勝ち候補の確認は別に 40 分。期待は 0〜15 Elo 程度だが、主目的は識別である。

task142 からなら改善し、task154 からは小さいなら、累積学習の仕方や逓減を優先して考える。両方弱ければ、round 2 の分布・教師や共通の学習量を疑う。ただし 154 と比べると行数が約 4% 違い、学習 seed は 1 回なので、原因を確定はしない。

必要な場合だけ `task154 → round 1、2 周` をもう 1 本追加する。これで初期値 2 種 × データ 2 種がそろう。追加は約 6 分 + J。**160 が明確に改善したら、まずこの追加判定は省き、量の試験へ進む。** 説明のために 2×2 を必ず完成させる必要はない。

### 3. 30 万局。60 万局は、その後の選択肢にする

**仮説:** 同じ 1,000 万行を繰り返すより、同じ更新数で違う局を学ぶ方が強い。

レシピ: 採用確認を済ませた eval B を固定する。B どうしで新 seed の **30 万局**を作る。生成・QS と初期重みは B に統一する。局 ID の hash 順で 15 万局を選び、残りと重ならない対照を作る。局単位 holdout を先に除く。

- 対照: 15 万局由来の約 10M 行を 2 周。
- 候補: 30 万局由来の約 20M 行を、対照と同じ総提示行数・更新数まで学習する。約 1 周に当たる。厳密な停止更新数を実装してそろえる。
- 同じ lr、batch、勝敗割合、初期値、学習 seed。データ範囲の違いを主に問う。広い方を 2 周する案は、この比較が有望だった場合の次の 1 本にする。

費用: 生成 5h + QS 34 分 + 学習 2 本で約 12 分 + 2J = **約 7.3h**。assemble / compact / 保存整理に別途 0.5〜2h、勝ち候補の確認に 40 分。全体で約 8.5〜10h を取る。Task 159 ではまとめと学習に約 1h かかっており、学習時間だけで全工程を見積もらない。

期待: B に +5〜25 Elo。広い方が同更新数でよければ、次に 60 万局を検討する。30 万局でも同じなら、量をもう 2 倍する前に順位 4・6 へ進む。60 万局の新規生成だけで 10h、QS 68 分になる。30 万局から同設定で追加するなら、追加分は生成約 5h + QS 34 分で済む。

**容量が実行前の条件である。** 既存方式は 15 万局一式で約 12GB。30 万局で約 24GB、60 万局で約 48GB の目安で、一時ファイルはさらに要る。空き 25GB のまま丸ごと追加しない。局の正本と provenance は永続領域に保持する。圧縮・復元照合、索引と source row の保持、分割した assemble / compact でピーク容量を抑える。再生成に何時間もかかる正本を消したり `/tmp` に逃がしたりしない。必要容量を確保できなければ、この実験は順位 4 より後にする。

### 4. 捨てた葉を、まず 100 万行だけ正しく戻す

**仮説:** 終盤寄りの情報を落とす損失があり、新しい局を作るより安く回収できる。

レシピ: まず Task 159 の既存棋譜を再利用する。QS を changed 保持の別出力で処理する。changed から固定 seed で一様に **100 万葉**を選び、task154 の **新しい depth-9 探索値**を付ける。元の根の評価値は引き継がない。未変更の既存 9.83M と結合する。初期値は task154。総提示数は既存 159 e2 と同じ約 19.7M にそろえる。

注意がある。**QS の PV 末端は、実際の棋譜に現れた局面とは限らない。** 手番反転を正しくしても、元棋譜の勝者がその枝でも勝つとは保証されない。最初の試験では、未変更行だけ勝敗 30%、追加した葉は再ラベル評価値だけにする。追加行の「結果を混ぜない」mask を明示し、真の draw と混同しない。この試験が問うのは「捨てた葉の評価情報を戻すと得か」である。勝敗込みの全復元とは分ける。

元局面と葉、PV、手番、内部 Value、元局 ID の対応を残す。独立 holdout とその反転、未変更行との重複を除く。再ラベルの履歴条件も固定する。まず 1 万行で到達深さと速度を測り、実行枠が膨らむなら標本数を減らす。

費用: QS 約 17 分、1M の d9 再ラベル約 10 分を基準に **15〜30 分枠**、学習約 6 分、整形 15〜30 分、J。合計約 1.6〜2.2h + 確認。再ラベル速度は Task 146 の約 1,800 行/秒からの外挿で、終盤の重い裾は未測定である。

期待: +0〜20 Elo。改善なら 300 万行、次に changed 全体へ広げる。中立なら、全 640 万行を先に再ラベルしない。悪化なら深さ・枝の勝敗・局面分布を切り分ける。Task 128 の +64 をそのまま期待しない。元教師もデータも違う。

### 5. drift が見えたら、既存の水匠データを 5% だけ replay

**仮説:** 自分の探索値に寄せるほど、水匠の軽い仕上げで得た汎化を一部失う。

レシピ: 同じ初期値と自己対局集合を使う pure 腕に対し、**提示行の 95% を自己対局、5% を既存の水匠 7.24M から**抽出する。20M 提示なら公開側は計 1M 提示。自己対局行だけ勝敗 30%、公開行は評価値だけ。総提示数・batch・lr・seed をそろえる。最初から公開データを追加取得しない。行の出典ごとに誤差を記録する。

費用: 整形約 10〜20 分、学習約 6 分 + J。pure 腕が既存なら約 1h、なければ対照分の J も追加。期待は +0〜15 Elo。

水匠保持が改善し、外部棋力もよければ、その小率を次ラウンドでも維持する。保持指標だけ改善して棋力が同じなら採らない。最後に水匠で全面的に再仕上げしてからしか測らない運用にはしない。自己対局の寄与が隠れる。

元 64M の一部を混ぜる案も候補だが、私は公開 5% より後に置く。旧 WS-T 系のラベルへ引き戻す力にもなるためである。作者が公開 replay を避けたい場合は、**元 64M から 10% 提示、残り自己対局 90%**を 1 本だけ試す。旧ラベル行は結果を混ぜない。費用はほぼ同じ。これは広い旧知識を残す比較であり、新しい教師情報を足す比較ではない。両 replay を最初から並べて判定しない。

### 6. 深いラベルは、同じ 100 万局面で対照を作る

**仮説:** 自己対局の数より、浅い教師の誤差が次の上積みを制限している。

レシピ: 採用済みの自己対局集合から、未変更の静止行 **1M** を固定抽出する。ply・評価帯の割合を母集団に合わせる。各回の生成 eval と同じ教師を使い、同じ局面・同じ履歴条件で d9 と d11 を付け直す。残りの行と総提示数は共通にし、その 1M のラベルだけ違う 2 腕を、同じ初期値から通常 2 周相当学習する。根の元値と冷えた TT の再ラベルを比較する交絡を避けるため、d9 側も新しく読む。

事前に各深さ 2,000 行、最大 20 分の pilot を置く。d10 / d11 / d12 の時間、実到達深さ、cap 到達、値の変化を見る。基本は d11。1M の予測が 45 分を超えるなら d10、20 分未満なら d12 を選ぶという時間規則を先に固定する。深い方でも cap で未達なら、その行は両腕とも対照の d9 値に戻し、実際に変更できた割合を報告する。

費用: pilot と d9 / 深い再ラベルで約 0.5〜1.5h、整形約 20 分、学習 2 本約 12 分、2J。**合計約 2.5〜3.5h + 確認**。古い Task 147 の 512 行では d12 は d9 の約 5 倍だった。今回の分布では再計測が必要である。

期待: +0〜20 Elo。深い腕が同条件の d9 腕にも現採用にも有望なら、2〜4M へ広げる。単なる教師間の相関改善では全量 d12 に進まない。小さい深い集合だけを何周も回して、Task 150 C のような偏った学習にしない。

### 7. 学習条件は 1 条件ずつ。まず lr を半分にする

**仮説:** 新しい自己対局目標への適合が速すぎて、追加の周で広い知識を失う。

最初のレシピ: 同じ集合・初期重み・2 周・batch 1024・勝敗 30%で、**lr だけ 1e-5 → 5e-6**。初期、半周、1 周、2 周を保存する。対局させるのは事前指定の final 1 本だけ。fresh Adam を両腕で統一する。

費用: 10M なら約 6 分 + J。20M なら約 12 分 + J。期待は +0〜10 Elo。教師への一致と外部棋力が両立するなら継続する。Task 150 で低 lr でも改善しなかったため、最上位には置かない。

次の 2 案は、診断が支持した場合だけでよい。

| 条件 | 固定するレシピ | 追加費用・判断 |
|---|---|---|
| 大きい batch | 1024 → 4096、lr は据え置き、同じ総提示行数 | 学習速度・VRAM は pilot、判定 J。更新数は 1/4 になるため「勾配ノイズだけ」の効果とは呼ばない。lr を同時に 4 倍にしない。初動の不安定さが見えなければ見送る |
| 勝敗割合の schedule | 2 周の前半 30%、後半 15%。単一 Adam を継続し、固定 30% と比較 | 学習約 6〜12 分 + J。大きな改善は期待せず 0〜10 Elo。効いても固定 15% よりよい証拠にはならない。そこを主張するなら固定 15% の追加対照が要る |

Task 155 は 15〜30% の広い良い領域を示す。50% は悪い。世代が進んだから結果率を上げる理屈はない。まず固定 30%を維持する。深いラベルへ移ったら、結果率を下げる方向の 1 点比較には意味がある。0 / 15 / 30 / 50 の総当たりを再開しない。

### 8. wide はデータを増やした後の条件付き候補

**仮説:** データを広げても小さいネットの近似誤差が残り、512x2-8-96 がそれを減らせる。

着手条件: 自己対局の利用可能行が 40〜60M 程度になり、量・再ラベルの比較を先に済ませ、保存容量と丸 1 日以上の空き枠があること。40M は必要量の証明ではなく、私の資源配分上の線引きである。**Task 160 の 20M が中立だっただけでは着手しない。**

レシピ: 256 の checkpoint をそのまま wide に読み込まない。まず Task 149 の経路で CUDA 1,000 更新の pilot。VRAM と速度を測る。本比較は **256 と 512 を同じ旧 64M・同じラベル・lr 6e-5・12 周・同じ seed でゼロから**作る。双方に既存水匠 7.24M の 2 周と、同じ新自己対局集合の 2 周を同じ条件で加える。段階ごとの final を固定する。比較するのは最後の 2 本。学習済み wide の export と専用エンジンで改めて 0cp gate を通す。

費用: 256 の土台だけで約 3.8h。wide の GPU 実速は未測定で、仮に 1.5〜2.5 倍なら約 6〜10h。仕上げ、pilot、2J、確認を含め **12〜17h 程度 + 時間制確認**を見ておく。新しい自己対局データの生成費はこの外である。pilot で予算を超えるなら打ち切る。

期待: −30〜+30 Elo 程度と広く見る。Task 149 の 0.97 倍 NPS はランダム重み・負荷下の参考値にすぎない。固定ノードで勝っても、学習済み同士の NPS と時間制で得があることを別に確かめる。大会 1 週間前から新構造の採用作業は始めない。私なら、この数日の第一陣には入れない。

### 今はしない: 玉の位置に合わせた学習の変更

Task 157 の +0.69pt は観測上の校正差であり、「囲わせれば得る Elo」ではない。居飛車だけでは差を確定できず、micro もその場ですぐ囲いへ動いていない。玉への手作り加点、囲いを強制する自己対局、中央行の大量除外はしない。

round 2 の同じ校正と分布をまず追う。誤差が持続し、外部相手での具体的な敗因も一致した場合にだけ、通常集合に対し「翼・自陣の行を最大 2 倍、置換は提示全体の 10% 以下」の 1 本を試す。手数・評価帯・飛車分類をそろえ、ラベル自体は変えない。整形数分 + 通常学習 + J、期待は 0〜10 Elo 程度。それでも玉の危険一般を直した証拠とはしない。Task 117 の難しい行の重み付け、134 の危険局面再ラベルが棋力改善を示さなかったことも重く見る。

## 4. Task 160 の結果で順序を変える

「悪い」は CI 上限 < 0。「中立」は 0 を含む。負の点推定だけで悪化確定にしない。e1 / e2 は別々に扱う。

| 結果 | 次の行動 | やめること |
|---|---|---|
| どちらかの CI 下限 > 0 | スクリプト所定の新組 + micro を完了する。両点推定が正なら作者の採用判断へ。通った版で本番確認を行い、順位 3 の 30 万局を優先。順位 2 の追加判定は省略可 | 160 の改善を「強い世代だけのデータがよい」と読まない。再利用した過去データも寄与しうる |
| e1 がよく、e2 が同等以下 | 同じ更新数で広いデータを学ぶ方を基本にする。30 万局でも 150k×2 周対300k×約1周から始める | 自動的に 2 周・4 周へ増やさない |
| e2 がよく、e1 は中立 | 現段階では量と更新数の組み合わせに価値がある。次の増量でも同更新数の対照を残す | 「データだけが原因」「周数だけが原因」と言わない |
| 両方中立 | 採用は task154 のまま。順位 2 を 1 本、その後は順位 4 の changed 再ラベルを量より先にする。drift があれば順位 5。量試験を行っても 30 万局で一度止める | 60 万局や wide を一晩の既定ジョブにしない。中立を救うための追加 seed 合算をしない |
| 一方だけ悪化、他方は中立 | 中立を主ケースとする。e2 だけ悪ければ過剰学習の仮説を重くし、低 lr または提示数抑制へ | 両方悪化した扱いにしない |
| 両方悪化 | task154 を保持。merge の行・ラベル対応、出典別件数、学習行順、初期 checkpoint、QS eval を小標本で確認。整合なら順位 2 と drift / 深いラベルへ。単純な量追加は止める | 自己対局全般の否定も、旧 64M の全面再学習も急がない |
| 主判定はよいが確認が負 | 未確認として採用しない。新しい機構の実験へ戻る。特定アンカーへの偏りも記録する | 確認 seed を取り直して通るまで試さない |

最初の 48 時間は、160 の所定判定、本番確認の枠、読み取り診断、分岐先の 1 実験までに絞る。その後の 2〜3 日で量か再ラベルをもう 1 件。順位 5〜8 を全部消化する予定にはしない。同じデータで安い学習候補を 10 本作ると、学習より判定に丸 1 日を使う。

## 5. 大会に向けた隠れたリスク

現在壊れていると確認した項目ではない。既存の検証結果と、次に残る確認を分ける。

| リスク | 確認すべきこと |
|---|---|
| **違う重みで指す** | task142 は best と final が違う。Task 145 では実際に周選択を誤った。学習 config → checkpoint → Factorizer fold / tie → BNNQ / BNQ2 → nn.bin → 実際の binary と YAML を SHA でつなぐ。`prod_start.sh`、`gen_config.py`、`check_kachi.py`、runbook の採用先を一致させる。現コードの prod は task154 の SHA を確認している |
| **古い対局やキャッシュの再利用** | `std_frame` の対局名は eval 名・seed・nodes に依存する。呼び出す `t106.done()` はファイル存在と終了記録で再利用を判定する。同じ名前の eval を上書きしない。モデル名は不変にし、binary / eval / option の manifest を保存する。train の resume も別出力にする |
| **0cp gate の確認範囲** | 静的 forward の一致は強い保証だが、差分更新の全履歴を証明しない。最終重みで既存 gate に加え、少数の合法手列の各時点を、履歴付きと SFEN からの再初期化で照合する。捕獲、成り、駒打ち、玉移動、入玉を含める。wide は学習済みの重みで専用 binary を指定する |
| **正しい単位、間違った勝敗混合** | 表示 cp と内部 Value を混ぜない。`--cp-result-lambda 0.7` は評価値 70%、結果 30%。実装は勝率空間で混ぜて内部値へ戻す。draw は既知でも混合対象外である。draw と欠測を分けずに変更すると、旧教師の欠測を引き分けとして学ぶ危険がある |
| **学習用の勝敗と本番裁定の差** | 自己対局は最大 320 手で draw、本番はブイ込み 512 手。生成器の連続王手反復は draw だが、本番の扱いとは違う。Task 156 の round 1 には該当例がなかった。以降も件数を記録する。QS の別枝へ元棋譜の勝敗を無条件に付けない |
| **merge の監査性** | 160 の merge は 64-bit hash で重複とみなし、同 hash の全列一致を検証しない。衝突や棋力への実害は未検出だが、「完全一致除去」の保証とは分ける。次版は同 hash 候補だけ全列照合する。また merge 出力には元の game ID / ply が残らない。出典と元行番号を sidecar に残す。局単位 holdout を merge 後の行分割で代用しない |
| **時間管理と時計** | WSL の時計で時間切れが実際に起きた。Xubuntu は再起動後も確認済みだが、NTP 同期表示だけで単調時計の正しさは保証できない。再起動・カーネル変更後は既存の時計測定を再実行する。設定の丸め、2 秒加算、ponderhit の負荷を本番経路で確認する。遅延余裕を推測で削らない |
| **測定条件と大会条件の差** | 主判定は 1 スレッド・10 万ノード、較正した弱い側のアンカー、乱数序盤、最大 320 手。本番は全力・時間制・定跡なし。ノードで同じでも NPS・並列探索・長期戦で得とは限らない。full Gikou2 に +217 は総合力の成果だが、現代の強豪への保証や NNUE 単独の効果ではない |
| **本番に試験用投了を持ち込む** | floodgate の投了中継は 10/19 に待ち時間を数える不具合を直した。本番 prod は通常の bridge 経路である。最終 YAML の engine path と `ResignValue` を見て、試験用 proxy と本番の方針を取り違えない。対局をまたぐ待機も含めて確認する |
| **容量と資源の競合** | 空き 25GB ではデータ生成中より assemble の一時物が危険になりうる。空き容量と inode の下限で安全に止まれるようにする。31GB RAM で判定 8 並列と大きい学習キャッシュを同時に持たない。本番や時間つき検証に学習・生成を重ねない。熱、更新、スリープ、ログ保存領域も最終確認する |

大会の 1 週間前には探索 binary、bridge、接続方式、構造を固定する。その後の eval 更新も、通常の採用確認と本番通し試験を終えられるものに限る。最終 48 時間は新しい学習案を始めず、配備物・設定・ログと復旧手順を確定する。既に検証された 256 幅の task154 を、いつでも戻せる基準として保管する。

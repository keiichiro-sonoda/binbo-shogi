# Task 034: NNUE の構造拡大 — 容量を増やしても度合いは伸びない(=データが主因)

## 結論

- **容量だけ**を変えて再学習した(目標=Task 033 の cp 回帰+clamp±5000+MSE、データ=既存流用、構造のみ拡大)。
  feature_dim を 32→64→128→256(hidden 16→32)に拡大。
- **容量を 8倍にしても評価の度合いは伸びない。** 頑健な val 指標(相関・decisive 符号一致・decisive 予測値の大きさ)は
  feature_dim 32→256 で**ほぼ横ばい**(val_corr ~0.74-0.75、decisive_sign ~0.80、|pred|_dec ~1300cp)。
  decisive 評価は容量に関係なく ~1300cp で頭打ち(クランプ目標±5000・技巧2の飛車得 ~2600 に届かない)。
- **容量はむしろ害**: forward が **fd256 で約5.2倍遅い**(6.2µs→32µs/局面)→ 同じ持ち時間での到達深さが
  **5.23→4.45 に低下**。棋力は **0-8 のまま**(fd256、技巧2 Lv1, 1秒)で、速度低下のぶん不利。
- **切り分け結論: 度合いの頭打ちの主因は容量ではなくデータ。** 器(fd=32)は既に足りており、増やしても学習信号(教師データ)が
  decisive の度合いを押し上げないため伸びない。**次段はデータ**(decisive 局面の重点化 / 教師拡充)。
- **採用モデルは据え置き = `model_cp_mse_c5000`(fd=32)。** 拡大版は遅いだけで利得ゼロなので不採用。
- Rust 推論はヘッダから feature_dim/hidden_dim を読むため**無改修で新次元を読める**(fd256 で数値一致を確認、最大誤差 3.0e-06)。

## 設計(容量だけ動かす)

- 変えたのは feature_dim / hidden_dim のみ(`train_nnue.py --feature-dim --hidden-dim` は既存引数。**コード変更なし**)。
- 目標・データ・スケールは Task 033 据え置き: `--objective cp --loss mse --clamp-cp 5000`、`/tmp/binbo-task017/cache`、`forward*600=cp`。
- 構造は 3 層(Linear feature_dim→hidden→hidden→1)を維持。Rust `nnue.rs` はヘッダの次元で動的確保するため、層数を変えない限り無改修。

## サイズ別の結果(val 指標は best epoch、cp/MSE/clamp5000、8 epochs)

| model | fd | hd | params | size | train/ep | val_corr | decisive_sign | \|pred\|_dec | \|pred\|_near |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **c5000(採用, fd32)** | 32 | 16 | 11.3M | 45MB | 24s | **0.750** | **0.807** | **1327** | 284 |
| fd64 | 64 | 32 | 22.6M | 87MB | 42s | 0.744 | 0.797 | 1303 | 288 |
| fd128 | 128 | 32 | 45M | 173MB | 80s | 0.743 | 0.805 | 1298 | 286 |
| fd256 | 256 | 32 | 90M | 346MB | 152s | 0.745 | 0.797 | 1308 | 295 |

- **全指標が横ばい。** feature_dim を 8倍にしても decisive 予測値(~1300cp)も相関(~0.74)も符号一致(~0.80)も改善しない。
- 代表4局面の静的分解能はノイズが大きく(fd64=6.47×、fd128=2.10×、fd256=1.74×、c5000=3.95×)、容量との単調関係なし。
  これは marginal 側の curated 2局面の読みが揺れるため(例 fd256 は startpos 512/quiet 630 と高め→分母大→低比率)。
  **頑健な指標(val の decisive/near 比 ~4.2-4.7、val_corr)で見るとサイズによらず一定。**
- 過学習: いずれも best epoch は早期(3〜6)、それ以降 val 微増。val と分解能の乖離(train だけ良くなる)は無く、
  容量で度合いが伸びないのは過学習のせいではない(そもそも伸びる兆候が出ていない)。

## 速度・サイズ(度合い改善ゼロ・コストだけ増)

- forward 速度(10,000局面の `nnue-eval`): **fd32(c5000) 0.062s vs fd256 0.320s = 約5.2倍遅い**(6.2µs→32µs/局面)。
- モデルサイズ: 45MB → 346MB(8倍)。学習メモリ: 1.16GB → 2.76GB。学習時間: 24s/ep → 152s/ep(6倍)。
- 探索への影響(技巧2 Lv1 1秒対局の平均到達深さ): **c5000=5.23 → fd256=4.45**。forward が重い分、同じ時間で浅くなる。
  Task 030 で確認した「生徒は十分深く読めている」優位を削る方向で、**度合い改善ゼロ + 深さ低下 = 純粋に損**。

## 効果確認(採用 c5000 据え置き、fd256 で切り分け確認)

- 棋力(`nnue-vs-gikou` Lv1, 1秒, 8局): **fd256 = 0-8**(c5000 も 0-8)。avg_depth 4.45(< c5000 5.23)。**勝ち星は動かず**。
- `nnue-diag` 符号一致(対技巧2 d8): fd256 = 22/25(88%)、c5000 = 21/21(100%)。**ほぼ同等**(別ラインの統計差)。容量で改善せず。
- スケール/数値一致: fd256 を export → Rust `nnue-eval` と Python forward が一致(`verify_nnue_rust` 最大誤差 **3.046e-06** < 1e-3, ok)。
  Rust はヘッダの次元で動的確保するため**新次元を無改修で読む**。スケールは `forward*600=cp` 維持。

## 切り分け(容量で伸びたか / データが主因か)

- **伸びなかった。** feature_dim 32→256(器 8倍)で decisive の度合い(~1300cp)・相関・符号は不変、速度だけ悪化。
- よって**度合いの頭打ち(技巧2の ~0.4倍)の主因は容量ではなくデータ**。器は fd=32 で既に足りており、
  教師データが decisive 局面で大きな評価を学ばせていない(near-equal 偏り / decisive 局面の信号不足)。
- **次段はデータ**: decisive 局面の比率を上げる(重点サンプリング/重み付け)、教師を増やす・深くする(`docs/BACKLOG.md` C)。
  容量拡大は「forward が律速になり、かつデータ側で度合いが出てから」検討(今回は時期尚早と判明)。

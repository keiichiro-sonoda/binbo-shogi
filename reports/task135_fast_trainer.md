# Task 135 — 学習器を速くする (計算の中身は変えない)

日付: 2026-10-18。マシン: 14700KF (Xubuntu), RTX 4060 Ti 16GB。
コード: `trainer/compact_cache.py`, `trainer/nnue.py` (`sparse_ft`), `trainer/train_nnue.py` (`--fast` ほか),
計測 `experiments/alphazero/t135_train_profile.py`, 一致の確かめ `t135_fast_equiv.py`, 学習し直し `t135_fast_retrain.py`。
実装の大部分は Codex (gpt-6.1-sol) に任せ, 使う行の取り方・判定の基準・確かめは Claude が直した。

## 1. どこに時間がかかっていたか (計測)
Task 129 の学習 (1 周 2,454 秒) の 1 歩 (1024 局面) を段ごとに同期して測った (`t135_train_profile.py`)。

| 段 | ms | 中身 |
|---|---|---|
| データの読み出し | 26.9 | 19.7GB の索引から, ばらばらな 1024 行をディスク (SATA の SSD) から読む。読んだ直後の行なら 0.03ms |
| 順伝播 | 14.5 | 重みの表 (176,745 × 256) 全体に Factorizer の足し合わせと量子化を毎回かける |
| 逆伝播 | 11.3 | 表全体の勾配 |
| Adam | 14.6 | 4,500 万個を 7 本ほどの処理で更新 |
| その他 | 1.1 | |

同期なしでは 45.8ms (2.2 万局面/秒)。1 歩で実際に使う行は約 1.4 万行 (表の 8%)。

## 2. 変更 (どれも新しいオプションのときだけ。既定の経路は変えていない)
| オプション | 中身 |
|---|---|
| `--compact-cache DIR` | 索引を玉の位置 (uint8 × 2) + 玉から見た駒の番号 (uint16 × 77) = 1 行 156 バイトにして GPU に常駐 (64M 行で 9.98GB)。変換時に全 63,950,000 + 50,000 行を元と照合して不一致 0, 例外扱い 0 (225 秒) |
| `--sparse-ft` | その歩で使う行だけ (`torch.unique`) Factorizer の足し合わせと量子化をして embedding_bag。逆伝播は `F.embedding` 経由 |
| `--fused-adam` | `torch.optim.Adam(fused=True)`。全行を毎歩更新する意味は同じ |
| `--async-loss` | 損失の合計を GPU 上で持ち, 途中保存と周の終わりだけ取り出す |
| `--fast` | 上の 3 つ (要 `--compact-cache`) |

Codex の初版は使う行の枠を 78,848 行に固定していて, 使わない枠が全部 0 番の行を指すため逆伝播がそこで詰まり, かえって遅かった (1 歩 93ms)。`torch.unique` に替えて 1 歩ごとに小さな同期が 1 回入る代わりに, 1.4 万行だけの計算にした。

## 3. 同じ計算か (GPU で 2,000 歩, `t135_fast_equiv.py`)
- 旧版を 2 回回すと 2,000 歩後も完全一致 (この GPU では揺らぎなし)。
- 足し算の順序を変えない `--compact-cache` と `--async-loss` は旧版と**完全一致**。
- 順序が変わる `--sparse-ft` と `--fused-adam` は, 小さな差が Adam で広がる。基準 = 旧版で各半分の特徴の並びを逆にした版 (同じ数式, 足す順序だけ違う):

| | 重みの表のずれ (RMS) | 最後 500 歩の平均損失の差 | 1 歩 |
|---|---|---|---|
| 基準 (並びを逆に) | 7.9e-4 | 145 | 40.1ms |
| `--sparse-ft` | 6.8e-4 | 65 | 17.8ms |
| `--fused-adam` | 8.1e-4 | 4 | 31.3ms |
| 全部 (`--fast` 相当) | 7.8e-4 | 95 | **8.9ms** |

- 1 歩目: 使う行だけの勾配と全表の勾配の差は最大 4.9e-4 (その成分の最大 5.7e3 に対し相対 8.5e-8)。fused と従来の Adam の差は 3 歩で 1.9e-9。
- 途中保存からの再開: 遅い経路 → 速い経路, 速い経路どうしとも, 中断なしと同じ続き (CPU で確認)。
- `--compact-cache` だけでは速く見えないのは, この試験では同じ行を 2 回目に読むので索引がメモリに残っていたため。本番 (64M 行をばらばら) ではディスクの待ちを消す。

## 4. 学習し直して強さを確かめる (事前登録 `t135_fast_retrain.py`)
Task 129 と同じ学習 (同じ seed・ラベル・12 周) を `--fast` で。

| | 採用 eval (Task 129) | 速い経路 |
|---|---|---|
| 1 周 | 2,454 秒 | 516〜556 秒 (平均 543 秒, **4.5 倍速い**) |
| 学習全体 | 約 8.2 時間 | **約 1.8 時間** |
| best epoch / val loss | 10 / 41,086 | 12 / 40,586 |
| 0cp の確認 | | GREEN (32/32) |

標準の物差し (候補 − 採用): **+24.2 Elo [+0.5, +48.2]** (tanuki- +19.0 [−16.4, +54.4], AobaNNUE +29.2 [−3.7, +61.8])。
判定 = **FAST_BETTER** (事前の取り決めどおり, 学習は速い経路に切り替える)。

読み: 差がないと予想していた。速い経路は足し算の順序の違いで別の学習の道筋をたどるので, seed を変えたのと同じ程度のばらつきが出うる。下限 +0.5 は 0 すれすれで, 速い経路そのものが強くする理由はない。**この生徒を採用 eval にするかは, 取り決め (`docs/evaluation_protocol.md`) どおり新しい seed で確かめてから。**

# 物差し(外部アンカー)の調査 — 2026-10-05

採用 eval `task107_student_64m` は技巧2@7 に 91%(+401)勝ち、物差しが飽和に近い。次の比較のために、どう測るかを調べた。

## 1. 手元で測ったこと(各 100 局、64M 学生、yane 100ms/Threads1、seeds 20271401-04)
| 候補 | 結果 | 判断 |
|---|---|---|
| 技巧2@7(現行) | 91%(+401、Task 107) | 飽和に近い。差が CI に埋もれやすい |
| **技巧2@8** | 91 勝 0 敗、**エラー 9 局(9%)** = 技巧2 が対局中に落ちる(`unexpected EOF`)。平均 depth 7.89 | **使えない**。エラー局は集計から外れるので、落ちやすい局面に偏りが出る。勝ち局だけでも 100% で物差しにならない |
| **tanuki- Háo(手元の smoke eval)を同じ 100ms で** | 9 勝 91 敗(**9%、−402**)、エラー 0、nodes 12.2 万 / 12.3 万 | 強すぎる(逆側に飽和)。ただし **安定していて、探索量を絞れば釣り合わせられる** |

- やねうら王には **`NodesLimit`(1 手の探索ノード数の上限)と `DepthLimit`** のオプションがある(手元のバイナリで確認)。強い相手のノード数だけ絞れば、ちょうどよい強さの相手を作れる。
- ただし今の対局ハーネス(`yane-vs-yane`)は**両側に同じオプション**しか渡せない。片側だけ NodesLimit や FV_SCALE を変えるには Rust 側の小さな変更が要る。

## 2. 外部の情報
- **Stockfish の fishtest**: 時間ではなく**ノード数を固定**した対局を使い、機械や負荷の違いによるばらつきを減らしている。本プロジェクトでも、GPU 学習と並走したときに nodes が 5〜6% ずれて `TIME_ASYMMETRY` が出た(Task 105)ので、同じ問題が起きている。
- **CCRL の gauntlet**: 測りたいエンジンの **±250 Elo 程度**に収まるアンカーを複数並べ、それぞれのレーティングを固定して測る。1 つのアンカーだと相性の影響を受ける(本プロジェクトでも Task 104 で直接 +134 / 技巧2@6 で +56 と食い違った)。
- **水匠5 の評価関数**: やねうら王のリポジトリで単体公開されている、本プロジェクトと同じ **NNUE halfKP256** 型の評価関数(推奨 FV_SCALE 24)。無償公開の最後の版。リリースページにライセンスの明記はなく(検索結果ではやねうら王側の GPLv3 との記述もあるが未確認)、**手元での練習相手としての利用に留め、学習データや大会提出物には使わない**前提なら問題になりにくい。正式に使う前にライセンスを確認する。
- **floodgate**(東大の自動対局サーバ): 2026 年も運用中。CSA プロトコルのクライアントで接続、`floodgate-300-10F`(5 分 + 1 手 10 秒)、30 分ごとに対局が組まれ、約 15 局でレーティングが付く。多様な相手に対する**絶対的なレーティング**が得られる一方、1 局 30 分枠で数日かかる、相手や機械がまちまちでばらつく、エンジンが公開の場で対局する(大会の取り込み禁止とは無関係だが、名前と棋譜が公開される)。

## 3. 推奨
1. **アンカーを複数持つ(2〜3 本)**、それぞれ採用 eval から ±250 Elo 程度に調整する:
   - 技巧2@7(継続。系列の比較用。ただし上限が近い)
   - **tanuki- Háo + NodesLimit**(ノードを絞って 60〜70% 程度に)
   - **水匠5 + NodesLimit**(ライセンス確認後。tanuki- とは別系統で相性の偏りを減らす)
2. **時間ではなくノード数で対局する**(自分側も固定ノード、例えば 10 万ノード)。GPU 学習と並走しても結果が変わらなくなり、`TIME_ASYMMETRY` が出なくなる。
3. ハーネスの変更: `yane-vs-yane` に**片側ごとの setoption**(NodesLimit、FV_SCALE など)と `go nodes` を足す(Rust の小変更 + `cargo test` / `verify`)。
4. 較正: 新しいアンカーごとに、採用 eval で別 seed の 200 局程度を流してノード数を決め(目標 60〜70%)、以後は固定。
5. floodgate は任意。年に数回の「絶対値の確認」用として価値はあるが、日々の比較には向かない。

## 4. 追記: 水匠5 のライセンス確認(2026-10-05)
**一次情報に明示的なライセンス表記は見つからなかった。**
- やねうら王リポジトリの単体リリース(`suisho5`)とブログ記事: 開発者たややん氏と相談して単体公開した、最新のやねうら王や「自作の探索部」と組み合わせてよい、という趣旨のみ。ライセンス・利用条件・再配布・学習への利用の記述はない。
- やねうら王 v7.00 と mizar 氏のビルドでは、GPLv3 のやねうら王実行ファイルに**同梱**して配布されていた(同梱版のリリースノートにもライセンス記述なし)。
- たややん氏の紹介記事(note)と X の告知: ライセンスの記述なし(「やねうら王の GitHub と Wiki をよく読んで」とだけ)。
- 日本語版 Wikipedia の情報欄は「GNU GPL v3」だが**出典がない**。
- ⇒ 判断: 「無償で公開され、エンジンと組み合わせて使うことが想定されている」のは確かなので、**手元で対局相手として動かすだけ**なら公開の趣旨の範囲内。ただし GPLv3 と断定できる一次情報はないので、**学習データ・蒸留の教師・配布物・大会提出物には使わない**(dlshogi と同じく封印側で扱う)。物差しに採るなら `docs/USED_COMPONENTS.md` にこの扱いを明記する。

**代わりの候補 = AobaNNUE(ライセンスが明確)**
- 作者 山下宏氏のリポジトリ(yssaya/AobaNNUE)が **GPL-3.0** を明示。第三者の再配布リポジトリによれば、作者が 2026-09-27 に「nn.bin も GPLv3」と明言している。
- 無償公開の評価関数として最強クラスとされる(2025 年 11 月時点の評価)。AobaZero の評価値から作った NNUE で、**系統が技巧2 とも tanuki- とも違う** = 相性の偏りを減らす物差しとして理想的。
- ただし構造が **HalfKP 768x2-16-64**(推奨 FV_SCALE 40)で、手元のやねうら王(halfkp_256x2-32-32 ビルド)では読めない。作者公開の GPL ソース(やねうら王 V9.00 ベース)から Linux 用に別ビルドが要る。強さは 64M 学生よりかなり上のはずなので、NodesLimit で大きく絞る必要がある。

## 5. 決定(2026-10-05、Keiichiro): 新しい物差し = **tanuki- Háo + AobaNNUE**(ノード数で強さを調整)

### 選定理由
1. **飽和の回避**: 採用 eval(`task107_student_64m`)は技巧2@7 に 91%。この先の改善(epoch 増・データ増)を見分けるには、採用 eval が 60〜70% 程度で勝つ相手が要る。技巧2 は depth 8 以上で対局中に落ち(実測 9%、エラー局が集計から外れて偏る)、これ以上強くできない。
2. **強さを連続的に調整できる**: どちらもやねうら王で動く評価関数なので、`NodesLimit`(1 手の探索ノード数)で強さを細かく合わせられる。同じ時間なら両者とも採用 eval より強い(tanuki- は実測 −402)ので、「絞る」方向だけで調整できる。
3. **ライセンスが明確**: tanuki- Háo は GPL-3.0(配布物に同梱)、AobaNNUE は作者リポジトリが GPL-3.0 を明示し、作者が nn.bin も GPLv3 と明言(2026-09-27)。水匠5 は一次情報にライセンス表記がなく(§4)、採らなかった。
4. **系統の違う 2 本で相性の偏りを減らす**: tanuki- は NNUE 自己対局・蒸留系、AobaNNUE は AobaZero(AlphaZero 型の自己対局)の評価値から作られた NNUE で、どちらも本プロジェクトの教師(技巧2、WS-T)とも系統が違う。1 本だけだと相性に引きずられる(Task 104: 直接 +134 / 技巧2@6 +56)。CCRL も複数アンカーで測る。
5. **安定性**: tanuki- は 100 局でエラー 0(技巧2@8 は 9%)。AobaNNUE も同じやねうら王系なので同様の安定性が期待できる(較正時に確認)。
6. **時間ではなくノード数で対局**(Stockfish fishtest と同じ): GPU 学習と並走しても結果がぶれない(Task 105 の `TIME_ASYMMETRY` の再発防止)。

### 使い方の決まり
- **測定用の対局相手としてだけ使う**。学習データ・蒸留の教師・定跡・配布物・大会提出物には使わない(自作 eval の系譜を汚さない)。
- 技巧2@7 は過去の系列との比較用に当面並べて測る。
- 較正: 採用 eval で別 seed の対局を流し、各アンカーのノード数を「採用 eval が 60〜70%」になるよう決めて固定。以後、アンカーの強さは変えない(変えるときは新しい物差しとして記録する)。
- 必要な作業: 対局ハーネスに片側ごとの実行ファイル・setoption(NodesLimit、FV_SCALE)と `go nodes` を足す(Rust、`cargo test` / `verify`)、AobaNNUE 用やねうら王(halfkp_768x2-16-64)を作者の GPL ソースからビルド。

# 評価関数の判定方法(標準、2026-10-06 決定)

新しい評価関数(候補)が採用中の評価関数(採用 eval)より強いかを、どう判定するかの正本。Task 108(物差しの較正)と Task 113(直接対局と物差しの食い違いの確認)を受けて決めた。

(`std_frame.measure_sets(..., which=std_frame.CONFIRM_ANCHORS)`)。

## 2026-10-19 午後の追加改定: 序盤が重ならない seed の組
Codex の Task 142 点検 (`reports/task142_review_codex.md`) で, 対局プログラムが序盤を `seed + 局番号/2` で決めるため, チャンクの seed を 1 ずつ
ずらした組では序盤がほぼ重なり, **1 組 800 局で違う序盤は 57 種類しかない** (3 組で 171) と分かった。以後の組はチャンクの seed を 100 ずつ離す
(1 チャンクの序盤は 50 種類なので重ならない, 1 組 400 種類): `s280` = 20280000 + 100i, `s281` = 20281000 + 100i, `s282` = 20282000 + 100i
(i = 0〜7, `std_frame.SEED_SETS`)。確認の組も同じく離す (`std_frame.spaced_set(base)`)。採用 eval は新しい組で指し直してから比べる。
旧 3 組 (std / conf135 / conf138) は `std_frame.OLD_SEED_SETS` として記録に残す。Task 142 の結論は序盤の重なりを考えた計算でも有意 (+29.5 [+15.4, +43.7])。

## 2026-10-19 の改定 (案 A: 3 組で比べる, 作者決定)
Task 138 で, 採用 eval の標準の組の成績がたまたま低く (対 AobaNNUE で他の 2 組より 20〜30 Elo 低い), 標準の組で採用 eval と比べた差が約 15〜20 Elo 甘く出ていたと分かった。ノード固定の対局は同じ結果を繰り返すので, 基準側の 1 回の運を全比較で共有してしまう。そこで以下に改める (下の 1〜5 のうち, これと食い違う部分はこちらが優先)。
- **主判定 = 3 組の seed をまとめた差**: 標準 20272001-08 (`std`), 20273501-08 (`conf135`), 20273601-08 (`conf138`)。各組・各物差し 800 局, 1 つの評価関数で 3 組 × 2 本 × 800 = **4,800 局**。採用 eval (task129) は 3 組とも指してある。共有序盤のペアで, 3 組 × 2 本をまとめて bootstrap (`std_frame.measure_sets` / `std_frame.delta_sets`)。組ごとの差は記述に留める。
  - CI 下限 > 0 → 強い / CI 上限 < 0 → 弱い / それ以外 → 区別できない (半幅 ≈ ±14 Elo)。
- **採用前の確認**: 3 組で「強い」と出た候補は, 新しい seed の組 (800 局 × 2 本, 候補と採用 eval の両方, 組は確認ごとに新しく取る) を指し, その組での差の点推定が > 0 なら採用候補 (採用は作者が承認)。3 組は以後の全候補で使い回すので, 多くの候補を試すと当たりを拾う偏りが出る。それを点推定の向きで確かめる (800 ペアで CI 下限 > 0 まで求めると +20 Elo 程度の改善がほぼ通らないため)。
- 採用 eval が替わったら, 新しい採用 eval を 3 組とも指してから比べる。
- **並列数 = 8** (`FRAME_PARALLEL`, 既定 8。**12 にしない**: やねうら王 1 本 約 1.2GB (置換表の既定 1GB) × 2 本 × 12 = 28GB で RAM 31GB を使い切りスワップした (10/20)。置換表を小さくすると探索が変わり過去の対局と比べられない)。Xubuntu で採用 eval の標準の組 1,600 局を 8 並列で指し直し, 16 ファイルすべてで勝敗・終わり方・手数・序盤が記録と一致, 919 秒 (4 並列の約 2 倍の速さ), CPU 最大 83°C。下の 8. (4 並列まで) は WSL のときの決め事。
- 過去 (Task 134 まで) の標準の組だけの判定は, 採用 eval 側の偏りの分だけ甘い (記録は書き換えない)。

## 決め事 (2026-10-06, 一部は上の改定が優先)
1. **主判定 = 外部の物差し**(Task 108 で較正したアンカー 2 本)。
   - **tanuki- Háo @4 万ノード、AobaNNUE @1.4 万ノード**(Task 186、2026-10-24 に採用 eval `task184_S_MR` に合わせて較正し直し。Task 127〜185 は @2 万 / @1 万, Task 108〜126 は @1 万 / @5 千)。確認用の micro は @1.55 万 (Task 186, 前は @1.1 万)。候補・採用 eval とも **10 万ノード固定**(`yane-vs-yane-ex --a-nodes 100000`)。
   - 各物差しに **800 局以上**(2 本まとめて 1 腕 1,600 局以上、半幅 ≈ ±28 Elo)。
   - 候補と採用 eval を**同じ seed**で当て、共有序盤のペアで差(候補 − 採用 eval)を bootstrap(`t103_absolute.paired_series_delta`、2 本まとめて)。
   - CI 下限 > 0 → 強い / CI 上限 < 0 → 弱い / それ以外 → 区別できない。
2. **直接対局(候補 vs 採用 eval)は参考扱い**。行う場合も判定には使わない(省略してよい)。
   - 理由: 直接対局は物差しより大きく出ることがある(Task 104: 直接 +134 / 物差し +56、Task 110: +37 / +16、Task 112: +38 / +21、Task 113: +68 / +19。Task 107・109 では一致)。食い違うときは常に直接対局が大きい。原因は未特定(候補が採用 eval の重みから学習を始めたかどうかとは対応しない)。
3. **標準の seed = 20272001〜20272008**(各物差し 8 かたまり × 100 局)。ノード固定の対局は再現するので、採用 eval 側の対局は同じ seed・同じ eval なら使い回す(今の物差しでは Task 127 で `task126_student_64m_factor_e24` の 800 局 × 2 本が既にある。ファイル名にノード数が入るので、古い物差しの対局と混ざらない)。候補は 1,600 局だけ指せばよい(4 並列で ≈ 30 分)。
4. **採用前の確認**: 標準の seed で「強い」と出た候補は、採用の前に**新しい seed**で候補・採用 eval の両方を各物差し 800 局ずつ指して確認する(同じ序盤で何度も候補を試すと、たまたま当たりの候補を選ぶ偏りが出るため)。確認でも CI 下限 > 0 なら採用候補。採用そのものは人間が承認する。
5. **判定は新しく指した対局だけで行う**。既に結果を見た対局を足して判定しない(「良くなるまで集める」になるため)。合算は記述に留める。
6. 事前登録(判定方法・seed・決定表を結果を見る前にコミット)は従来どおり。
7. 物差しの強さ(ノード数)は変えない。採用 eval が物差しに 9 割前後勝つようになったら(目安 0.8 超)較正し直し、新しい物差しとして記録する。手順は Task 108 / 127 と同じ: 同じエンジンでノード数を 2 倍刻みのはしご(各 104 局、標準とは別の seed)→ 勝率 0.65 に最も近い段(0.55〜0.75 の範囲内)→ その段で採用 eval の標準 frame を指して基準にする。物差しが変わる前後の比較(古い物差しの Elo と新しい物差しの Elo)は直接比べない。
8. 並列数は 4 まで(6 並列で CPU が 100°C に達し熱 guard が停止した。ノード固定なので並列数は結果に影響しない)。

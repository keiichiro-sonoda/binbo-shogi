# binbo の歩み

binbo は 2026-06-20 に始めた将棋 AI の個人開発である。最初の構想から何度も方向を変えており, この文書はその経緯を章ごとにまとめたもの。
数字の根拠と細部は各章に挙げた `reports/taskNNN_*.md` にある。日付順の一覧は [年表](timeline.md), 段階ごとの詳しい記録は [`STATUS.md`](../../STATUS.md)。

効かなかった試みも, 効いたものと同じ形で残している。判定の基準は実行前に決めて固定し (事前登録), 結果を見てから基準を動かさないようにした。

## 第 1 章 自前のエンジン (2026-06-20〜06-25, Task 001〜055)

**最初の構想**: ルール以外の人間の知識を与えず, 家庭用の計算資源で作者より強い将棋 AI を作れるか。

- 合法手生成は `yasai` に任せ, perft の完全一致で正しさを確かめた。その上に USI エンジン, αβ 探索, 置換表, 反復深化, 指し手の順序付け, 時間管理を自前の Rust で書いた (Task 021〜028)。
- 評価関数は KP / HalfKP の NNUE。教師は技巧2 の探索値を蒸留したもの (Task 015〜017)。Python で学習し, Rust の推論と数値が一致することを確かめた (Task 018, 020)。
- 強さの伸び悩みを, 容量・データ量・正則化・特徴量の順に切り分けた (Task 029〜053)。データを増やすと過学習がほぼ消えて初めて勝てたが (Task 041), 表現 (KPP など) を広げても強さは動かなかった (Task 052, 053)。
- dlshogi の公開モデルを使った蒸留も試したが, 素朴な置き換えでは弱くなり採用しなかった (Task 054, 055。モデルは私的使用の条件なので, 学習済みのものはこのリポジトリに含めない)。

報告: [`reports/task021_nnue_engine.md`](../../reports/task021_nnue_engine.md) 〜 [`reports/task053_kav2_kpp.md`](../../reports/task053_kav2_kpp.md)

## 第 2 章 探索をやねうら王に任せる (2026-06-26〜06-30, Task 056〜072)

- 自前の探索で一通りの理解を得たところで, **対局の探索はやねうら王に任せ, 評価関数で勝負する**方針に変えた (Task 056)。自前の探索のコードは `src/` に残している。
- 自作の学習器から, やねうら王の評価関数の形式へ書き出す道具を作り, 整数演算の評価値が **0cp で一致**することを確かめた (Task 058, 059)。
- 技巧2 から蒸留する教師を 800 万 → 1,600 万 → 3,200 万局面と増やすと伸びた (Task 062, 064)。
- 一方, 自分で指した局面を足して教師を育てる「自己強化」は, 量を増やしても, ラベルを自分のものに替えても弱くなった (Task 066〜071)。技巧2 の深さ 8 の探索値が, 蒸留の天井になっていた。

報告: [`reports/task056_yaneuraou_pivot.md`](../../reports/task056_yaneuraou_pivot.md), [`reports/task071_self_anchor.md`](../../reports/task071_self_anchor.md)

## 第 3 章 AlphaZero の寄り道 (2026-07-01〜09-12, Task 073〜103)

技巧2 に無い情報を, 家庭用の GPU で作れるかを試した章。全体の地図は [`docs/PROJECT_MAP_057-085.md`](../PROJECT_MAP_057-085.md)。

- Pgx (JAX) を選び (Task 073〜074), どうぶつ将棋で自己対局の学習が回ることを確かめてから (Task 075), 本将棋へ進んだ。
- 方策も技巧2 から温めて始めると, 自己対局の学習で初期値を有意に超えた (+133 Elo, Task 080)。ただしこの「内部の」強さは, αβ の相手との対局 (外部) には移らなかった (Task 083)。
- 81 マスを 81 トークンとして扱う Transformer (WS-T) を作り, 同じ規模の CNN より方策・価値とも良くなった (Task 087)。
- 自己対局のループの改善を評価関数の教師へ運ぶ経路は, 方策でも価値でも閉じていた (Task 091〜098)。
- 代わりに, **WS-T に 1 手先の探索 (Gumbel MCTS, 8 回) を足したもの**を評価関数の教師にすると, 同じ規模の技巧2 の蒸留より強い評価関数ができた (Task 100〜103)。

報告: [`reports/task080_m4_policy_warmstart.md`](../../reports/task080_m4_policy_warmstart.md), [`reports/task087_t1_transformer_warmstart.md`](../../reports/task087_t1_transformer_warmstart.md), [`reports/task103_scale_8m_sims_absolute.md`](../../reports/task103_scale_8m_sims_absolute.md)

## 第 4 章 教師と測り方を作り直す (2026-09-30〜10-19, Task 104〜143)

- 3,200 万局面の探索ラベルで学習した評価関数が, 技巧2 蒸留の最良に **+134 Elo** で, 初めて蒸留の天井を越えた (Task 104)。データを 6,400 万局面に増やし, 学習率と周数, Factorizer を詰めた (Task 107〜126)。
- **強さの測り方を決めた**: 直接対局は差が大きく出すぎることがあったので, ノード数で強さを合わせた外部の物差し (tanuki-, AobaNNUE) との対局で判定し, 採用の前に新しい組で確かめる (Task 108, 110, 127。[`docs/evaluation_protocol.md`](../evaluation_protocol.md))。
- 駒の取り合いの途中の局面を静止局面に置き換え, **同じ教師でラベルを付け直す**と効いた (Task 128, 129)。置き換えてラベルを引き継ぐだけ, 捨てるだけでは効かなかった (Task 106, 119)。
- 損失の形, 難しい局面の重み付け, 教師の分布の較正, 特徴量の左右反転などは効かず, その結果も残した (Task 111〜132)。
- 公開教師データ (水匠5 depth 9, nodchip 氏, MIT) で最後に軽く仕上げると伸びた (Task 142, 143)。

報告: [`reports/task104_32m_decisive.md`](../../reports/task104_32m_decisive.md), [`reports/task129_qs_relabel_64m.md`](../../reports/task129_qs_relabel_64m.md), [`reports/task142_public_suisho5.md`](../../reports/task142_public_suisho5.md)

## 第 5 章 自己対局と公開データ (2026-10-19〜10-25, Task 145〜188)

- 公開データだけでゼロから学習した「水匠5 の生徒」が, 自前の系統より強かった (Task 145)。
- 自分のソフトどうしを 15 万局, 詰みまで指させ, すべての局面に本当の勝敗を付けたデータで仕上げる「雑巾絞り」が効いた (Task 153〜155)。自分の探索の評価値を付け直すだけでは弱くなった (Task 147, 150)。
- 2 周目の自己対局, データの統合, 深いラベルは追加の改善にならなかった (Task 159〜164)。
- 2026-10-24, **大会の土台を水匠5 の生徒にする**と決めた ([`docs/decision_2026-10-24_student_base.md`](../decision_2026-10-24_student_base.md))。公開データを正面から使い, 独自性はその上に足したものと測り方で示す。技巧2 から育てた系統は止めた。
- 生徒に自己対局と公開データを混ぜて仕上げ (Task 181〜184), 公開データを 2 倍にした生徒が今の採用の評価関数 (Task 188)。

## 第 6 章 大会に向けて (2026-10-13〜)

第 7 回世界将棋 AI 電竜戦本戦 (2026-11-14〜15) に binbo として出る。CSA の通信, 先手 3 分・後手 10 分の時計, 切断からの再接続を, 手元のサーバと floodgate で試した。
先手 3 分の時計の使い方 (Task 180) と, 大会用のやねうら王の速いビルド (Task 178, ソースは無改変) もこの時期の作業。大会の本番用の道具と手順書はこの公開には含めていない。

## 進め方について

- 開発には AI のコーディングエージェント (Claude Code, Codex CLI) を使った。実装・実験の実行と集計・報告の下書きの多くはエージェントが行い, 何を試し何を捨てるか, 判定の決まり, 採用する評価関数は作者が決めた。報告の中の「Codex の点検」などはその記録。
- エージェントの出力は外部の正解に照らして確かめることを決まりにした (perft の完全一致, やねうら王との評価値の 0cp 一致, 外部の物差しとの対局)。
- 計算に使ったのは自宅の PC (Core i7-14700KF, GPU 1 枚) で, 2026-10-24 からは自宅の Xeon 機も判定の対局に使った。クラウドの計算資源は使っていない。

学習済みの重み, 教師データ, 外部エンジンの実体, 大会の本番用の道具と手順書, 機械に固有の監視の道具。
報告や `STATUS.md` にはそれらへの言及が残っているが, 中身はここには無い。
